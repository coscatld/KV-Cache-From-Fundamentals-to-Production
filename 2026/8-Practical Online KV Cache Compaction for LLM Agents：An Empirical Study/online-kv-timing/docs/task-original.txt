# 任务：实现 Agent 在线 KV Cache 自适应压缩时机实验

你是一名熟悉 LLM 推理引擎、KV Cache 管理、Agent 系统和实验设计的研究工程师。请基于当前仓库实现一套可复现的在线 KV Cache 压缩实验，用于验证自适应压缩时机相对于固定压缩时机是否具有优势。

本任务的目标不是直接提出复杂的新压缩算法，而是严格控制变量，建立可靠的实验基线，验证自适应策略的有效性、代价及适用条件。

## 一、研究假设

在 Agent 多轮检索和工具调用过程中，KV Cache 的增长速度、历史信息的未来相关性以及任务执行阶段均可能变化。

固定压缩策略可能存在两个问题：

1. 压缩过早：未来仍可能需要的历史信息被删除，影响任务质量。
2. 压缩过晚：KV Cache 占用持续增长，增加显存压力和推理成本。

核心假设：

在相同峰值 KV Cache 约束及可比的资源预算下，基于运行时可观测信号决定压缩时机，可能比固定压缩时机获得更好的任务质量—总耗时权衡。

该假设必须通过实验验证，不能预设成立。

## 二、第一阶段：审计现有代码，禁止直接重写

先检查仓库结构、依赖、模型加载方式、Agent 执行流程、检索工具、KV Cache 生命周期和现有测试。

重点确定：

1. 当前使用的模型、推理框架及其版本。
2. KV Cache 的创建、更新、读取、释放和压缩入口。
3. 是否能够获取每层、每个 KV head 的 Key、Value 及当前缓存长度。
4. 当前是否已有 Token Eviction（TE）实现，以及其 Token 重要性评分、保留比例和压缩逻辑。
5. Agent 每轮结束、检索返回、工具调用及模型生成结束时有哪些可观测事件。
6. 如何测量 KV Cache 实际显存占用、压缩耗时、模型生成耗时、检索耗时和工具调用耗时。
7. 当前是否具备固定数据集、验证集、测试集及已有的任务质量评估程序。

优先复用现有实现，不得为方便实验而重写整个推理引擎。

如果当前引擎不支持可靠的 KV Cache 访问或压缩，先实现最小可行适配层，并明确说明其限制。禁止通过只删除对话文本、重新拼接 Prompt 或清空缓存来冒充真正的 KV Cache 压缩。

第一阶段完成后，输出简短审计报告，列出代码入口、数据流、需要修改的模块、无法直接实现的功能和解决方案，然后继续实施，不要停留在报告阶段。

## 三、实验范围与控制变量

第一轮实验固定：

- 一个模型。
- 一个 Agent 检索基准。
- 一套系统提示词、工具定义和生成参数。
- 同一套 TE 实现。
- 同一组任务样本、随机种子和评估规则。
- 同一目标 KV Cache 压缩预算。
- 同一峰值 KV Cache 上限。
- 相同的检索和工具权限。

优先使用仓库现有且能够稳定复现的模型与基准。如果现有环境不具备运行条件，先提供可运行的小规模实验配置，不得擅自假设硬件或模型已经可用。

**第一阶段不引入 AM、额外拟合网络或其他复杂压缩算法。** 先以 TE 为统一压缩方法，减少额外优化步骤造成的混杂因素。

## 四、实现五组核心实验

所有组使用相同的 TE 实现、任务集合及评估方式。

### A. 即时 Boundary

每轮 Agent 交互完成后，在合法的轮次边界执行压缩。

使用固定保留比例和预先定义的 Token 重要性评分规则。

作为固定时机的基线之一。

### B. 固定延迟 1 轮

轮次完成后暂不立即压缩，等待后续一轮产生实际生成的 Query，再对待压缩历史缓存执行 TE。

明确区分：
- 被压缩的历史轮次。
- 用于评分的后续生成 Query。
- 当前尚未完成、不能压缩的活动轮次。

不得将未来 Query 用于它尚未产生时的压缩决策。

### C. 固定延迟 3 轮

等待 3 轮后再执行压缩。

需要明确延迟期间历史缓存如何增长，以及是否存在峰值显存超限。如果在达到延迟轮数前已经触及安全阈值，应记录触发原因并执行预先定义的安全回退策略。

### D. 固定延迟 5 轮

同样等待 5 轮，但必须处理缓存增长和显存压力。

不能通过忽略等待期间产生的 KV、缩短任务轨迹或改变生成行为，制造虚假的延迟压缩优势。

### E. 自适应压缩时机

实现一套简单、可解释、能够部署的自适应触发策略。

先考虑以下可观测信号：

1. 当前 KV Cache 长度及预计显存占用。
2. 距离上次压缩经过的轮数。
3. 新增历史 KV 的增长速度。
4. 当前 Query 与近期 Query 的分布变化程度。
5. 可选的检索结果重复率、工具响应新增信息量等 Agent 级信号。

不要求第一版同时使用所有信号。优先实现一个低开销策略，避免引入额外大型模型或昂贵的在线优化。

触发规则必须满足：

- 不访问未来尚未产生的信息。
- 不使用测试集标签或最终答案。
- 不依赖人工观察后手动决定何时压缩。
- 能够解释每一次压缩的触发原因。
- 设定明确的最小压缩间隔、最大允许间隔和显存安全阈值。
- 达到安全阈值时允许强制压缩，并将其计入实验统计。

如果采用 Query 分布变化作为信号，必须明确具体计算方式，例如对最近若干轮 Query 的归一化表示计算余弦距离或其他可复现的漂移指标。不能只写“根据 Query 变化自适应”。

## 五、严格分离自适应时机与自适应保留比例

这部分是实验设计的关键，必须独立实现和评估。

### 实验组 T：只自适应压缩时机

- 使用固定保留比例。
- 仅根据运行时信号决定何时压缩。
- 不动态修改 Token 重要性评分方法。
- 不动态改变目标保留比例。

### 实验组 R：只自适应保留比例

- 使用固定压缩时机。
- 根据运行时信号调整保留比例。
- 不改变触发时机。

### 实验组 TR：同时自适应时机与保留比例

只有在 T、R 两组独立完成后才实现。

通过消融比较 T、R、TR，分析收益分别来自触发时机、保留比例，还是二者的交互作用。

自适应保留比例必须有明确的上限、下限、更新规则及资源约束。不得将其与自适应时机合并成一个不可解释的黑盒策略。

## 六、验证集调参，测试集只做最终评估

按照任务或独立问题实例划分训练开发数据、验证集和测试集。若不涉及模型训练，至少确保策略选择与最终测试严格隔离。

要求：

1. 在验证集选择 Query 漂移阈值、压缩触发阈值、最小压缩间隔和其他策略参数。
2. 测试集只使用已经冻结的规则。
3. 不得根据测试集表现反复修改策略后仍将其作为独立测试结果。
4. 对所有实验组使用相同的数据划分。
5. 固定生成参数和随机种子；如成本允许，增加重复运行以评估随机性。
6. 记录配置文件、代码版本、模型版本、数据版本和实验时间。
7. 采用配对比较，尽可能让不同策略处理相同的任务实例。

如果验证集需要选择多种阈值组合，应实现统一的配置搜索程序，并记录所有候选策略，避免只保留表现最好的结果而忽略搜索成本。

## 七、必须计入全部额外开销

每次任务至少记录以下指标：

### 任务质量

- 官方基准任务得分或准确率。
- 任务成功率。
- 必要时的答案完整性与正确性指标。
- 重复检索率、重复工具调用率。
- 任务失败类型及失败原因。

### KV Cache 与显存

- 压缩前后 KV Token 数量。
- 实际 KV Cache 字节数。
- 峰值 KV Cache 占用。
- 进程峰值显存占用。
- 每次压缩的耗时。
- 压缩执行次数。
- 强制安全回退次数。
- 延迟压缩期间新增的 KV 数量。

### 总任务耗时

- 模型 Prefill 耗时。
- Decode 耗时。
- Query 收集与统计耗时。
- 压缩算法耗时。
- 检索耗时。
- 工具调用耗时。
- 因压缩造成的额外 Prefill、缓存重建或其他开销。
- 端到端总任务耗时。

总耗时必须按真实执行时间测量，不能只累计模型生成时间而忽略压缩、检索和工具调用。

并行执行时应区分端到端墙钟时间和各模块耗时，避免将并行时间重复累加后当作真实总耗时。

如果重复检索或工具调用的增加由压缩策略引起，必须计入相应的时间和调用成本。

## 八、相同峰值 KV 约束下比较质量—耗时关系

所有核心对照组必须满足同一个预先定义的峰值 KV Cache 上限。

不能只让延迟压缩组拥有更大的显存预算，也不能通过删除仍然需要的活动轮次 KV 来满足约束。

同时明确区分：

- 压缩比例。
- 保留比例。
- 实际峰值 KV Cache 占用。
- 峰值进程显存占用。

这些概念不能混用。

如果固定延迟 3 轮或 5 轮在给定上限下不可行，应如实报告其不可行率或安全回退情况，不得静默跳过失败样本。

除固定预算实验外，建议在可行范围内扫描多个保留预算，绘制任务质量—端到端总耗时曲线，并标注各策略对应的峰值 KV 占用。

如果某种策略在质量、总耗时和峰值占用上均不差于另一种策略，可以分析其是否形成更优的 Pareto 权衡。

## 九、实现与测试要求

采用清晰的模块化结构。具体文件位置以现有仓库为准，避免机械地创建重复模块。

建议拆分为：

- `compression/`：TE 实现及缓存压缩接口。
- `policies/`：Boundary、固定延迟、自适应触发策略。
- `metrics/`：KV 占用、时间、任务质量和工具成本统计。
- `experiments/`：统一实验入口、配置加载、批量执行。
- `configs/`：模型、基准、预算和各策略配置。
- `tests/`：单元测试、缓存一致性测试、策略测试和资源约束测试。
- `results/`：结构化实验记录和汇总报告。

以上是建议结构，必须优先适配现有仓库，而不是强制迁移目录。

至少覆盖以下测试：

1. TE 的保留 Token 数量符合预算。
2. 压缩前后 KV 的层、head、序列维度与数据类型正确。
3. 不会误删系统前缀、必要的结构性 Token 或尚未完成的活动轮次。
4. 延迟策略不会读取尚未生成的 Query。
5. 自适应策略严格遵守安全阈值与最小压缩间隔。
6. 自适应时机和自适应保留比例可以分别启用和禁用。
7. 统计的总耗时与真实任务生命周期一致。
8. 实验中断后能够恢复任务，并避免重复计入已完成样本。
9. 小规模合成测试与真实模型测试分开报告。

- 先审计，再修改；先跑通最小实验，再扩展规模。

- 不得将测试集用于触发规则调参。
- 不得同时修改多个实验因素后，直接将收益归因于自适应压缩时机。
